# Code Review Conventions for Metadata

> Area: 09-devops-sfdx-and-release-management · Currency: **Summer '26 (API 67.0)** · Status: 🌱 learning · Phase: 17

**Scope:** Reviewing a pull request whose diff is mostly XML nobody wrote by hand. Automated checks are [16](16-code-analyzer-v5.md) and [18](18-linting-formatting-and-pre-commit.md); this note is the human protocol and the opinion behind it.

## Core idea

Salesforce code review fails for a structural reason: **most of the diff was generated by a retrieve, and the reviewer knows it.** Once a PR is 3,000 lines of XML the reviewer's honest options are to read none of it or to block the release, and everyone picks the first. The convention that fixes this is not a longer checklist — it is **making the diff small enough to be worth reading**, then reviewing hard.

The second structural problem is that a metadata change's blast radius is invisible in the diff. Renaming a field is three lines; the consequences are somewhere else entirely, in things the XML never mentions.

## How it works

- **Ban unrelated retrieves.** A PR contains the components the story touched. `.forceignore` and a scoped manifest are review tooling, not deployment tooling.
- **Profiles are the worst offender** — retrieving one pulls every field permission in the org. Move access to permission sets and keep profiles out of the diff → [07-security · 03](../07-security-and-sharing/03-profiles-and-the-permission-set-led-model.md).
- **Review the four things a machine cannot judge:** sharing and execution context, guest-user reachability, whether new automation belongs in the existing trigger path, and whether a change to shared metadata affects a team that is not in the room.
- **Require the deployment plan in the description**, not just the code: pre-steps, post-steps, order, and what happens if it half-succeeds → [12](12-metadata-coverage-and-manual-steps.md).
- **Flows get read, not skimmed.** The XML is unreviewable, so review the change in Flow Builder and paste the reasoning; **Visual Flow Version Comparison** now does the diff for you → [04-flow · 24](../04-flow-and-automation/24-flow-deployment-versioning-and-governance.md).
- **Ownership by directory.** `CODEOWNERS` over `force-app/main/default/objects/` costs nothing and stops silent shared-schema changes.

> **From my notes** — via [INVENTORY.md](../_notion-seed/INVENTORY.md), since the vault holds the inventory line and not the note body — phase 16 recorded that. A 2023 field-migration checklist starts with *"change the field label and relationship label and rel API name"* and then spends the rest of itself chasing **report types missing in one environment and fields absent in two others**. The durable lesson is that **report types are built on relationship paths**, so renaming a relationship silently commits you to a report-type deployment — in every environment, in the right order. Nothing in the field's diff says so. This is the canonical example of blast radius living outside the change.

## Gotchas

- **An API-name change is a delete and a create.** The pipeline will happily deploy the new one and leave the old one in place, in production, holding data.
- **Picklist value changes do not deploy the way you expect** — deploying the field does not remove values from the org, and record-type assignments are separate metadata → [01-admin · 04](../01-admin-and-declarative-platform/04-record-types-and-picklist-architecture.md).
- **Reordering inside an XML file is not a change.** Retrieves are not stably ordered; teach reviewers to ignore pure reorder hunks rather than to argue about them.
- **A deleted component is invisible in a normal deploy.** Removing a file from git does not remove it from the org → [25](25-deployment-rollback-hotfix-and-destructive-changes.md).
- **`<apiVersion>` drift** in a bundle is a real change hiding in a boring line. It alters runtime behaviour, especially around the security defaults.
- **"LGTM" on a Flow means nobody looked.** Flow XML cannot be read; if the review comment does not describe the *behaviour*, the review did not happen.
- **Permission set changes need a named grantee.** "Adds View All on Case" is a review decision, not a diff line → [07-security · 15](../07-security-and-sharing/15-auditing-and-troubleshooting-access.md).

## Recall

Q: Why does a large metadata PR get rubber-stamped?
A: Most of the diff is machine-generated XML, so reading it is not rational — the fix is a smaller PR, not a longer checklist.

Q: What makes profiles poisonous in a pull request?
A: Retrieving a profile brings every field-level permission in the org with it, drowning the real change.

Q: What does renaming a relationship commit you to?
A: A report-type deployment — report types are built on relationship paths, and nothing in the field's own diff says so.

Q: Why is an API-name change dangerous even when the deploy succeeds?
A: It is a delete-and-create; the old component stays in the org with its data unless it is explicitly destroyed.

Q: How should a Flow change be reviewed?
A: In Flow Builder, with the behavioural reasoning written into the PR — with Visual Flow Version Comparison doing the version diff.
