## Problem Records DLOs stop silently dropping failed ingestion rows

_Gap-fill: Summer '26 (catalogued June 2026), not previously captured in this radar._

When a row fails ingestion into Data 360, it used to be **dropped**. The new **Problem Records DLO** captures those failures into a dedicated Data Lake Object instead — a DLO being the raw, untransformed landing table Data 360 writes source data into, before you map it to a DMO (Data Model Object, the harmonized, business-shaped version). So instead of noticing a shortfall weeks later by comparing row counts, you now query the failures directly, see the reason, and fix the mapping or the source. Practically, this changes the ingestion runbook: after every ingestion run, the Problem Records DLO becomes the first thing you check, and it belongs in a monitoring dashboard rather than in a one-off investigation.

**Why it matters for a Salesforce AI practitioner.** Silent data loss is the most dangerous failure mode in an agent stack, because it doesn't produce an error — it produces a *confident, wrong answer*. An agent grounded on Data 360 cannot tell the difference between "no matching record exists" and "the record failed to ingest last Tuesday." This feature converts an invisible correctness problem into a visible, queryable operational one, which is exactly what you want before you let an agent answer customers from that data.

**Status:** GA — Summer '26 release, listed under June 2026 in the Data 360 monthly release notes.

## Result Reuse for Data 360 Live and multi-currency reporting

_Gap-fill: Summer '26 (catalogued June 2026), not previously captured in this radar._

Two smaller Summer '26 items worth knowing. **Result Reuse for Data 360 Live** improves dashboard responsiveness by reusing query results rather than recomputing them for every viewer or refresh — "Data 360 Live" being the mode that queries source systems at read time (the zero-copy path) instead of serving from ingested copies. Zero-copy trades storage cost and freshness lag for query cost and latency, and Result Reuse blunts the latency side of that trade. **Currency Reporting in Data 360** adds accurate multi-currency handling so figures roll up correctly for organizations transacting in several currencies.

**Why it matters.** Result Reuse is the interesting one architecturally: the standard objection to zero-copy federation is "every dashboard load hits the warehouse and costs money and seconds." Caching at the result layer is how that objection gets answered, and it makes zero-copy a defensible default for more workloads rather than a niche choice. Do check the freshness semantics before you rely on it — a reused result is by definition not a live one, and for agent grounding, "how stale can this be?" is a design decision, not a detail.

**Status:** GA — Summer '26 release, listed under June 2026.

## Data 360 named as the grounding layer in the VA Agentic ELA

On **July 24, 2026**, the U.S. Department of Veterans Affairs awarded Salesforce a contract worth up to **$1.6 billion** over three years, and the announced architecture names **Data 360** alongside **MuleSoft** for integration and **Tableau** for analytics, underneath Agentforce agents doing contact-centre support, patient triage and care coordination. The reason this belongs in a Data Cloud note rather than only in the Agentforce one: it is a public, very large validation of the position Salesforce has been arguing all year — that Data 360 is not a CDP or a warehouse but the **context engine that grounds agents**. The VA use cases are grounding-hard, not agent-hard: triage and scheduling across 40,000+ provider services fail on data unification and identity resolution long before they fail on reasoning.

**Why it matters for your study plan.** It's the clearest available evidence for how the pieces are sold together, which is what you'll be asked to defend in a design review or an interview: MuleSoft moves and exposes the data, Data 360 unifies and resolves identity, the agent reasons over that context, Tableau observes the result. Note the target — reducing average appointment scheduling from **28 days to minutes** — and note that it is a target, not a delivered outcome.

**Status:** Announced July 24, 2026. Contract awarded; implementation not yet delivered.
