**All 24 phases are complete — 238 topic files across 10 areas, every `INDEX.md` row a live link.** What remains is not authoring but **maintenance**: the standing rules below are the vault's error-detection machinery, and phase 19 demonstrated why they have to be re-run rather than trusted. Its own verification pass overturned a phase-18 finding that was **one release old**.

**Phase 21 added a second kind of maintenance run.** Phases 19–20 audited the vault for *currency* — facts that had gone stale. Phase 21 audited it for **coverage**, by taking a standard advanced-Apex syllabus and grepping the vault for each item, and found four topics with zero hits anywhere. The two audits find different defects and neither substitutes for the other: a note can be perfectly current and the area around it still have a hole. The coverage grep is cheap and should be re-run whenever an area is declared complete.

**Phase 22 is what happens when the coverage audit is pointed at a whole subject rather than an area**, and it produced the build's first new area since the skeleton — the [10-soql-and-sosl](10-soql-and-sosl/INDEX.md) slot that this README had reserved from the start. Three findings generalise beyond it. **(1) A subject split across areas has no owner.** SOQL was covered five ways — language in 02, performance in 08, endpoints in 06 — and the *language* was nobody's, which is how SOSL ended up with eight lines. **(2) A ✅ can record an intent rather than an outcome.** `_notion-seed/INVENTORY.md` marked a *Group By Rollup* page as consumed into `02-apex · 03`; that note contains no `ROLLUP` and never did. This is a new failure mode for this file — not a wrong fact, an absent one marked present. **(3) The date discipline failed again.** Verifying `Database.Cursor` for the cross-store table found `CURRENCY.md`'s own *"myth corrected in phase 04"* callout asserting GA at Summer '24; Summer '24 was **Beta** and **GA is Spring '26, API 66.0**. Phase 13 already wrote the rule — *verify a date against the source, not against another note in the vault* — and phase 04's error survived eighteen phases underneath it, inside the file that exists to catch exactly this. **The specific trap is that *introduced* and *generally available* are different events.**

**Phase 23 found the failure mode that a two-vault split creates: a subject each side assumes the other owns.** Phase 22's finding was a subject with no owner *inside* `SF_core/`. This is the same defect across the boundary — `SF_core/README.md` sends Agentforce to `AI_Data/`, `AI_Data/` covers agents rather than Apex, and the *programmatic* AI surface fell down the gap: `ConnectApi`, `aiplatform`, `ModelsAPI`, `EinsteinLLM`, `createEmbeddings` and `capabilityType` returned **zero hits in either vault**, while [02-apex · 22](02-apex-and-triggers/22-invocable-apex-and-agentforce-actions.md) had covered the annotation that lets something else call Apex since phase 05. **A cross-vault boundary needs the coverage grep run across both sides, not within one** — a rule that generalises to every future area added beside an existing one. Two smaller findings. **(1) An absence in a class reference is evidence, but not of a retirement.** The 67.0 `ConnectApi.EinsteinLLM` page lists two static methods and the widely-taught `generateMessages` is not among them, with no deprecation notice anywhere — so the note states the absence and hedges the cause, which is the discipline phases 13 and 22 arrived at from the opposite direction. **(2) A plan's own research table can be wrong.** This phase's approved plan listed `numGenerations` and `temperature` as properties of `EinsteinPromptTemplateGenerationsInput`; verifying against the class reference before writing showed neither exists. The rule that caught it is rule 3 — *research before writing, never from recall* — applied to a plan rather than to a release note.

## Standing rules for every phase

1. Write **only** the listed files plus that area's `INDEX.md` row updates. Never let a phase sprawl.
2. **Hard cap ~80 lines per file.** If a topic won't fit, split the taxonomy rather than writing long.
3. Every 🆕 topic is researched against Summer '26 release notes **before** writing.
4. Every ⚠️ topic **opens with a one-line "What changed"** correction, before `## Core idea`.
5. Cross-link into `AI_Data/` rather than duplicating Agentforce/Data 360 content; link to `AI_Data/05-release-radar/` for currency detail.
6. Where [_notion-seed/INVENTORY.md](_notion-seed/INVENTORY.md) maps an old note to the topic, harvest the genuine gotcha into a `> **From my notes.**` callout — **and correct it if stale.** Never copy verbatim.
7. New platform jargon → [AI_Data/GLOSSARY.md](../AI_Data/GLOSSARY.md).
8. One commit per phase: `SF: phase NN — <title>`. Flip the ⬜ to ✅ in this table in the same commit.

## Post-phase check

```powershell
# no topic file over the cap
Get-ChildItem SF -Recurse -Filter *.md |
  Where-Object { $_.Name -notin @('INDEX.md','PHASES.md','CURRENCY.md','README.md','INVENTORY.md','_template.md') } |
  ForEach-Object {
    $n = @(Get-Content $_.FullName).Count
    if ($n -gt 85) { "$($_.Name): $n lines" }
  }
```

> **Fixed in phase 08, two bugs.** It used `(Get-Content … | Measure-Object -Line).Lines`, which **does not count blank lines** — an 81-line file reported as 59, ~27% low, so the `-gt 85` gate was really at ~117 real lines and had never fired. It also scanned `INDEX.md`, `PHASES.md`, `CURRENCY.md` and `INVENTORY.md`, none of which the cap applies to; with the count fixed those became permanent false positives.

Then grep the phase output for `WITH SECURITY_ENFORCED`, `sfdx force:`, `if:true`, `Locker`, `CometD` — each may appear **only** inside a ⚠️ correction, never as current guidance. - **`skinny table` described as self-service**, or as something you can view in Setup. It is a Support request, invisible to you, and re-requested every time the field set changes.
- **`delete` described as freeing storage or restoring performance immediately.** Soft-deleted rows keep costing both until physically purged.
